# Mail App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `mail`, the second app of the `hub-apps` tap: the agent searches, reads and writes the user's Feishu enterprise, QQ, Gmail and Outlook mail from chat through the pinned himalaya CLI, sends nothing until the user replies with a one-time code, adds a mail section to the hub's daily and monthly reports, and optionally alerts on urgent mail through carillon.

**Architecture:** Text for the agent (one `mail` skill with reference files, `SETUP.md`, `REMOVE.md`, default rules, two report sections) plus one Python CLI, `mail/scripts/mx.py` (PEP 723, run with `uv run`), backed by the package `mail/scripts/mailkit/`. The CLI is the agent's only way to the mailboxes. It generates the himalaya and carillon configs from `mail/mailboxes.toml`, reads himalaya's output through one parse layer, hands every piece of mail content to a tool-less `claude -p` call (the isolated reader) and gives the agent only fixed fields, sends free text that comes from mail straight to the user's private chat with `cc-connect send`, and holds every outgoing mail behind a one-time code that only the chat sees. Alerts come from `mx watch`, a user service that supervises carillon and sweeps every 15 minutes. Per-machine state (secrets, generated configs, drafts, marks, verdicts) lives outside the hub.

**Tech Stack:** Python ≥ 3.11 (stdlib `email`), tomli-w, pdfplumber, pytest, ruff, uv; external tools himalaya v2.2.1, carillon v0.2.0, ortie v2.3.0, Claude Code CLI (`claude`), cc-connect ≥ 1.5.0, cc-hub ≥ 0.7.0; GreenMail 2.1.3 (CI only).

**Spec:** `docs/superpowers/specs/2026-10-16-mail-design.md` (Chinese). Read it before any task. Platform contract: `docs/apps.md` ("Reports") and `src/cc_hub/templates/skills/hub-apps/authoring.md` in `C:\dev\cc-hub`. Exact commands of the external tools: "External tool facts" below.

## Decisions this plan adds to the spec

The spec leaves these to the implementer (§13) or let Claude decide; the plan fixes them so that tasks agree:

1. **Report window.** The sections use `CC_HUB_REPORT_SINCE` and `CC_HUB_REPORT_UNTIL` instead of a time the app keeps (§7). cc-hub moves the window on only when the report went out or was empty, so a report that failed to send is covered again by the next one; a time kept by the app would move on regardless and lose that mail. The first run still covers 24 hours.
2. **Reply drafts written by the reader never reach the agent** (§8.2 says the agent then edits them). The draft goes to the chat with its code; the agent changes it by passing the user's words to `mx revise`, which asks the reader again, or replaces the body with text it writes itself. This keeps §8.1's rule that free text from mail has no way into the agent.
3. **The reader is Claude Code only.** `claude -p --tools ""` has no tools; `codex exec` 0.162 always has a shell, even read-only, and could read the secrets. A hub whose agent is Codex still needs the `claude` CLI installed and logged in; `SETUP.md` says so (§8.1, last point).
4. **carillon and ortie are installed when needed**, not listed in `requires` (which cc-hub always installs): ortie when an Outlook mailbox is added, carillon when alerts are turned on. Both through `mx install-tool`.
5. **Installs run the app's own downloader**, `mx install-tool <tool>`: one line on every platform, which downloads from the official GitHub release and checks the pinned SHA-256 before it unpacks anything (§4.1).
6. **More than three urgent mails in one batch make one combined alert** (absolute rule 6), for example after the server was down.
7. **Codes** are 6 digits, stored as a salted scrypt hash, valid 24 hours, void after 3 wrong tries (§8.2 fixes one-time use, content binding, 24 h and hashing).

## Review Focus

1. **A misled agent guessing or reusing codes.** Wrong codes, a code of another draft, the same code twice, a draft edited after its code went out (also by editing the state file directly): none may send. After 3 wrong codes the code is void. Tests: Task 10 (`test_three_wrong_codes_void_the_code`, `test_code_of_other_draft_refused`, `test_draft_file_edited_behind_the_script_voids_code`).
2. **An alert storm.** First start with a full inbox, a UIDVALIDITY reset, or a server that was down for a day must not send one message per mail. Tests: Task 11 (`test_first_run_sets_baseline_without_new_mail`, `test_uidvalidity_change_falls_back_to_date`), Task 12 (`test_catch_up_after_downtime_sends_one_combined_alert`).
3. **Odd mail.** HTML-only mail, GB18030/GBK subjects and bodies (common from QQ and Chinese senders), mail without a text part, very long mail. The reader and the chat get readable text. Tests: Task 8 (`test_gb18030_html_only_mail_reads_as_text`, `test_long_body_cut_at_limit`).
4. **The chat is unreachable** (cc-connect stopped) when a code or an alert goes out. A code nobody saw must not stay valid; an alert is queued and sent later. Tests: Task 10 (`test_confirm_fails_cleanly_when_chat_unreachable`), Task 12 (`test_alert_queued_when_chat_down_and_sent_later`).
5. **A draft or original longer than one chat message.** It is split at line breaks, every part arrives, and the code is in the last part, after everything the user must check. Tests: Task 9 (`test_long_text_split_at_lines_max_4000`), Task 10 (`test_long_draft_splits_with_code_last`).

## External tool facts

Read from the sources at the pinned tags on 2026-10-19 (nothing was run). Full notes with source links: `C:\Users\Jenwein\AppData\Roaming\Claude\side-session-notes\local_76d98ef1-b122-4f28-9483-54d12195c4a2\mail-tools-research.md`. Where a fact is marked *unverified*, the task that depends on it checks it first.

- **F-CLI (all three tools).** Global flags before the subcommand: `-c <path>` (split on `:`; hence the relative-path rule), `-a <account>`, `--json`, `--log-level <off|error|warn|info|debug|trace>`, `--log-file <path>`. There is no `-o`. Data **and errors** go to stdout; stderr carries only logs (off by default). An error exits 1 and, with `--json`, is `{"error": "...", "sources": ["..."], "backtrace": null}` on stdout. JSON is compact when piped. With `stdin` closed and `--json`, no wizard prompt can start.
- **F-AUTH (secrets).** A password or token is `{ command = [...] }` (an argv array runs without a shell on every OS; prefer it) or `{ raw = "..." }`. The command gets a null stdin; only its first stdout line, CR/LF trimmed, is used; a non-zero exit is an error.
- **F-HCONF (himalaya config).** Per mailbox `[accounts.<name>]`: `email`, `display-name`, `mailbox.alias.<role> = "<server name>"` for `inbox`, `sent`, `trash`, `archive` (IMAP gives only INBOX a role; there is no SPECIAL-USE, so every role used needs an alias); `imap.server` = `imaps://host:port` (TLS), `imap://host:port` (cleartext, or with `imap.starttls = true`); password login `imap.sasl.plain.username` + `imap.sasl.plain.password.command`; OAuth `imap.sasl.xoauth2.username` + `imap.sasl.xoauth2.token.command`; QQ's ID `imap.id.auto = true` + `imap.id.fields = { name = true, version = true, vendor = true, support-url = true }`; the same `smtp.server` (`smtps://` / `smtp://` + `smtp.starttls`) and `smtp.sasl.*`. Backend tables reject unknown keys. Leave `message.send.save-copy` unset.
- **F-JSON (himalaya JSON keys).** v2.2.1 writes kebab-case keys (`message-id`, `has-attachment`) for envelopes, mailboxes and flags, snake_case for `imap status` and `imap fetch`; 3.0 will switch to camelCase. `himalaya json-schema <key>` prints a command's schema (keys such as `himalaya-envelope-search`, `himalaya-mailbox-list`, `himalaya-imap-status`, `himalaya-imap-fetch`, `himalaya-imap-search`, `himalaya-account-check`, `himalaya-message-send`, `himalaya-message-add`).
- **F-LIST (folders).** `mailbox list` → `{"mailboxes": [{"id", "name", "role": "inbox"|null, "total", "unread"}]}`. Non-ASCII names come back in IMAP modified UTF-7 (`&...-`, *unverified*); use the name as given for aliases and `-m`, and decode it only to match and to show.
- **F-QUERY (search).** `envelope search -m <folder> -s <page size> -p 1 <query...>`, all flags before the query, which is the remaining words. Grammar: `date D` (that day), `after D` (strictly after the day), `from P`, `to P`, `subject P`, `body P` (case-insensitive substring; quote `P` as `"..."` with `\"` and `\\` escapes), `flag seen`, combined with `and`, `or`, `not`, parentheses; then `order by date desc`. There is no `before`: "before D" is `not after <D-1>`; "since D" is `after <D-1>`; "unseen" is `not flag seen`. Dates use the `Date:` header. A non-ASCII term makes himalaya send `CHARSET UTF-8`, which Outlook rejects. Output `{"envelopes": [{"id", "message-id", "flags": [{"raw", "iana"}], "subject", "from": [{"name", "email"}], "to": [...], "date": RFC 3339 | null, "size", "has-attachment": bool | null}]}`; `has-attachment` is filled only with `--has-attachment`.
- **F-UID (ids and catch-up).** An envelope `id` is the IMAP UID. `imap status <folder>` → `{"uid_next", "uid_validity", "messages", "unseen", ...}` (the only way to see UIDVALIDITY). `imap fetch -m <folder> "<uid-set>" --internal-date` → `{"messages": [{"uid", "internal_date", ...}]}`; `"<n+1>:*"` returns the highest message even when nothing is newer, so keep only `uid > n`. `imap search -m <folder> --since YYYY-MM-DD` (INTERNALDATE) → `{"uid_mode": true, "ids": [{"id"}]}`.
- **F-READ (reading).** `message read <id> -m <folder> --raw` (no `--json`) writes the exact message bytes to stdout and never sets `\Seen` (peek is the default; `--seen` would mark it). For many mails in one session (some servers cut off after about a dozen logins in a row): `imap fetch -m <folder> "<uid,uid,...>" --body` → `body` is the base64 of the exact bytes, also without `\Seen`.
- **F-SEND (sending).** `message send --no-save` with the message on stdin. Recipients come from To, Cc and Bcc; himalaya strips Bcc before sending. Stdin is read line by line as UTF-8 and **stops silently at the first invalid line**, so the message must be 7-bit (RFC 2047 headers, base64 or quoted-printable bodies). Success: `{"message": "Message successfully sent"}`.
- **F-SAVE (sent copies).** `--save <mailbox>` would append after sending, and a failed append would then look like a failed send. So send with `--no-save`, then append the copy separately: `message add -m <sent folder> -f seen` with the same bytes on stdin → `{"id": "<uid>" | null, "sent": false}`.
- **F-MOVE (mark and move).** `flag add -m <folder> <id> -f seen`; `message move <id> --from <folder> --to <folder>` → `{"message": "..."}` only, and **exit 0 even when nothing moved** (`"No message moved: ..."`): check the text. On a server without MOVE, himalaya copies, flags and expunges only the moved UIDs (the standard move; the mail stays in the target).
- **F-NODEL (never).** `message delete` (permanent inside the trash), `imap expunge`, `--seen`. The fake himalaya fails on any of them.
- **F-CHECK (doctor).** `account check` → `{"account", "backends": [{"backend": "imap"|"smtp", "ok", "error"}]}`, exit 0 even when a backend fails.
- **F-CAR (carillon).** Its own config `[accounts.<name>]` with `imap.mailbox = "INBOX"` (required, one per account), `imap.server`, `imap.sasl.*`, `imap.id.*` as for himalaya, and `imap.hook.on-message-added.cmd = [argv]`; IDLE by default, or `imap.watch.poll.interval = <seconds>` to poll instead. The hook gets environment variables only (`id` = UID, `mailbox`, `subject`, ...; no account name, so put the mailbox in the argv) and runs synchronously on that account's thread: keep it fast. Reconnects and restarts do **not** replay mail that arrived meanwhile, and a UIDVALIDITY change rebaselines silently: the app's own catch-up is required. Run: `carillon -c carillon.toml --log-level warn watch` (all accounts, until SIGTERM/Ctrl+C, then exit 0). Whether carillon needs D-Bus on a headless Linux is *unverified* (the GreenMail test in Task 12 runs it headless).
- **F-ORTIE (Outlook OAuth).** ortie stores no token: `storage.read.command` must print the token JSON, `storage.write.command` receives it on stdin. Config `[accounts.<name>]`: `client-id = "9e5f94bc-e8a4-4e73-b8be-63364c29d753"` (Thunderbird's public Microsoft client, which ortie's README offers; ortie has none of its own), `endpoints.authorization` / `endpoints.token` = `https://login.microsoftonline.com/common/oauth2/v2.0/{authorize,token}`, `endpoints.device-authorization` = `.../devicecode`, `endpoints.redirection = "https://localhost"`, `scopes = ["https://outlook.office.com/IMAP.AccessAsUser.All", "https://outlook.office.com/SMTP.Send", "offline_access"]`, `grant = "device"` or `"authorization-code"`, `auto-refresh = true`, the two storage commands. Sign-in: `ortie -a <name> --json auth get` prints `{"device_code", "user_code", "verification_uri", ...}` (device grant) or `{"authorization_uri", "state", "pkce_code_verifier"}` (code grant); then `ortie -a <name> auth resume <device_code>` polls until approved, or `ortie -a <name> auth resume --state <s> --pkce <v> '<redirected URL>'`. Whether Thunderbird's client allows the device grant is *unverified*; the code grant works but needs the user to paste the URL their browser was sent to (`https://localhost/?code=...`) — into the server terminal, never the chat. Token for himalaya and carillon: `ortie -c ortie.toml -a <name> token show --auto-refresh` (no trailing newline). Two refreshes at the same moment may race (*unverified*).
