# mail 应用设计

日期：2026-10-16
所属 tap：`hub-apps`（公开仓库 `Jenwein/hub-apps`）
目标 cc-hub 版本：带"日、月、季、年汇报机制"的版本（另行设计，见 §11）

标注约定：没有标注的内容是用户的决定；标"（Claude 定）"的是 Claude 替用户做的选择，用户可以改；标"（留给实现者）"的由实现者决定。

本设计从头来过，不沿用 2026-10-16 撤回的上一版邮件应用（自己实现 IMAP/SMTP 的 `mk`）的任何设计或裁定。

---

## 1. 这是什么，为什么做

用户在聊天里用一句话管理自己的多个邮箱：问它"今天有什么要处理的邮件"、"QQ 邮箱有没有收到验证码"，让它"用 Gmail 给 Cursor 发邮件，说我忘了关自动续费，想退款"，每天收到一份需要关注的邮件汇报，查"QQ 邮箱历史上发过哪些邮件"。可选地，重要邮件（例如"订阅扣款因余额不足被拒"）到达后几秒到几分钟内在聊天里提醒。

所有收发都交给 [himalaya](https://github.com/pimalaya/himalaya)（邮件命令行客户端），实时提醒的监听交给同一作者的 [carillon](https://github.com/pimalaya/carillon)。应用自己不实现任何邮件协议，只做三件事：把用户的意图变成 himalaya 命令、按规则判断哪些邮件重要、守住安全边界（§8）。

## 2. 目标、非目标、绝对不能出的错

**目标**

- 第一版支持四个邮箱：飞书企业邮箱、QQ 邮箱、Gmail、Outlook。
- 按需查询：跨邮箱、按邮箱、文件夹（收件箱、已发送）、时间、发件人、主题、正文组合查询；找验证码；查已发送的历史。
- 代写代发：用户说意图，agent 写草稿，用户确认后才发；回复、转发同样。
- 收发附件。
- 按用户明确要求把邮件标成已读、移到归档或垃圾箱。
- 每日汇报里的邮件一段、每月汇报里的邮件一段（§7），挂在 cc-hub 的汇报机制上。
- 可选的实时提醒（默认关闭），靠服务器推送触发，不靠频繁轮询（§6）。
- 默认有一套判断规则，用户可以在聊天里改（§5）。

**非目标**

- 163/126、mail.com（mail.com 的 IMAP 可能要付费版，先不做）。
- 自己实现 IMAP/SMTP 或在本地另存一份邮件库、全文索引。
- 接飞书开放平台的邮件接口（飞书邮箱走 IMAP，和其他三个一样）。
- 用另一个系统账户隔离邮件服务（§8.4）。
- 从 Bitwarden 取密码：留给以后的密码应用，本应用只留好接口（§4.3）。
- 永久删除邮件、自动回复、自动退订、日历邀请处理、PGP（Claude 定）。

**绝对不能出的错**

1. 没有用户在聊天里回复确认码就发出任何邮件，包括回复和转发（§8.2）。
2. 照邮件里的文字行事：邮件内容永远只是资料。自动运行（实时提醒、每日汇报）时，能执行命令的 agent 看不到邮件正文和附件（§8.1）。
3. agent 读到、说出或提交任何邮箱密码、授权码、令牌；它们进 git 或聊天。
4. 永久删除邮件。
5. 读信时把邮件标成已读，改变用户手机上看到的未读状态（只在用户要求时标）。
6. 实时提醒刷屏：同一封信提醒两次；"立即提醒"以外的信打扰用户。
7. 静默失败：登录失效、监听停掉了却不告诉用户。
8. 编造验证码、金额、日期、收件地址：它们必须来自邮件本身或用户。

## 3. 国际化

给 agent 读的文字（skill、`SETUP.md`、`REMOVE.md`、提示词、默认规则）用英文写；agent 跟用户说用户的语言；用户自己写的规则用用户的语言（Claude 定，与其他应用一致）。

## 4. 邮箱和软件

### 4.1 软件

| 软件 | 用途 | 版本 |
|---|---|---|
| himalaya | 所有查询、读信、发信、附件、标记、移动 | 锁定 v2.2.1 |
| carillon | 实时提醒的监听（IMAP IDLE） | 锁定 v0.2.0 |
| ortie | Outlook 的 OAuth 令牌，自动续期 | 锁定 v2.3.0，只在用了 Outlook 时需要 |
| uv | 运行应用自己的脚本 | 不锁 |

- 版本锁定。上游出新版时定期同步：每月汇报里检查三者在 GitHub 上的最新版本，有新版就告诉用户；升级由应用发新版完成（改锁定的版本、跑完测试），不在用户的机器上自动升级。
- 只从官方 GitHub 发布页下载，并核对校验值（Claude 定）。三者都有 Linux、macOS、Windows 的现成程序；具体安装行写进 `app.toml` 的 `requires`（留给实现者）。
- himalaya v2 是 2026 年 7 月的重写版，JSON 输出还在变（3.0 会把字段名改成 camelCase），所以脚本只通过一层自己的解析读 himalaya 的输出，并用 `himalaya json-schema` 在测试里核对（Claude 定）。

### 4.2 每个邮箱的接法

| 邮箱 | 登录 | 推送 | 用户要先做的事 |
|---|---|---|---|
| 飞书企业邮箱 | 专用密码 | IMAP IDLE | 管理员开启第三方客户端；用户生成专用密码 |
| QQ 邮箱 | 授权码，需要 IMAP ID | IMAP IDLE（服务器声明支持，未实测） | 设置里开启 IMAP/SMTP，生成授权码 |
| Gmail | 应用专用密码 | IMAP IDLE | 开两步验证，生成应用专用密码 |
| Outlook | 只能 OAuth（ortie） | IMAP IDLE | 在服务器终端里做一次授权（§4.3） |

- himalaya 和 carillon 只认出收件箱，"已发送"等文件夹要按邮箱配置名字（例如 QQ 是 `Sent Messages`，Gmail 的名字随界面语言变）。设置时用 `himalaya mailbox list` 找出来，拿不准时问用户（Claude 定）。
- 发信后是否往"已发送"里存一份，按邮箱定：服务器自己会存的（例如 Gmail）不存，否则会重复（留给实现者逐个邮箱实测）。
- QQ 的 IMAP ID、飞书的服务器地址和 Outlook 的 OAuth 流程，都要在验收时用真实邮箱确认（§12）。

### 4.3 密码和令牌

- 授权码、专用密码由用户自己在服务器终端里输入（应用提供一条命令，输入时不回显），存在总站之外、只有用户的系统账户能读的位置，不进 git（Claude 定具体做法：一个按系统放置的文件，限制为只有本人可读；实现者可以换成系统钥匙串，但必须在三个系统和无图形界面的 Linux 上都能用）。
- Outlook 的 OAuth 授权也由用户在服务器终端里完成；令牌由 ortie 保存和续期（留给实现者选 ortie 的授权方式，优先不需要把任何回调地址贴进聊天的方式）。
- himalaya 和 carillon 的配置里只写"运行时用哪条命令取密码"，不写密码本身。以后接密码应用，只改这条命令。
- agent 看不到也不读取密码。登录失效（授权码被撤销、改了主密码、OAuth 令牌失效）时，在聊天里告诉用户是哪个邮箱、怎么重新登录，每次失效只说一次，恢复后不再提（Claude 定）。

### 4.4 数据放在哪

- **总站数据目录 `mail/`（进 git，不含任何秘密）**（Claude 定）：
  - 邮箱清单：每个邮箱一条，含名字（例如 `qq`）、地址、服务商、服务器、文件夹名字、发信是否存副本。它是唯一的来源，himalaya 和 carillon 的配置都由脚本从它生成。
  - 用户自己的规则（§5）。
- **每台机器自己的状态（不进 git）**（Claude 定，位置留给实现者）：生成出来的 himalaya 和 carillon 配置、每个邮箱最后处理过的邮件（UID 和 UIDVALIDITY）、等待确认的草稿、实时提醒的分类记录、下载的附件。
- 不在本地保存邮件正文的副本；查询都实时去服务器查。

## 5. 判断规则

- 由 AI 读邮件按规则判断，不需要用户预先写死条件。规则用自然语言写。
- 应用自带一套默认规则（在应用目录里，随升级更新）；用户自己的规则在 `mail/` 里，叠加在默认规则之上，冲突时以用户的为准（Claude 定）。用户在聊天里说"以后 GitHub 的通知都忽略"，agent 改用户规则并提交。
- 默认规则分三档：
  - **立即提醒**（开了实时提醒时）：钱出了问题（扣款失败、卡被拒、余额不足、服务因欠费即将停用）；账户安全（异地或新设备登录、密码或两步验证被改、不是用户发起的验证码或重置邮件）。
  - **进每日汇报**：真人写给用户、在等回复的信；几天内到期的事（续费提醒、账单到期、证件或域名到期）；订单、快递状态变化；账单和收据。
  - **忽略**：营销、订阅资讯、社交平台通知。
- 判断由 §8.1 的隔离读信完成，规则作为它的输入。

## 6. 实时提醒

- 默认关闭；用户在设置时或之后在聊天里打开、关闭。只在一台机器上运行（总站跑 cc-connect 的那台），哪台由设置时记下（Claude 定）。
- **监听**：carillon 对每个邮箱的收件箱保持 IMAP IDLE 连接，断线自动重连。新邮件到达时，carillon 的 `on-message-added` 钩子调用应用的脚本。
- **常驻**：设置时在用户同意后装成用户级的后台服务（Linux 和 WSL 用 systemd，macOS 用 launchd，Windows 用计划任务），开机自动运行；卸载应用或关掉实时提醒时移除。
- **应用脚本接手后**（Claude 定）：
  1. 记下每个邮箱最后处理过的邮件；每次被调用时把上次之后的新邮件全部找出来，所以断线期间到的信也不会漏。carillon 重连后不一定补报断线期间的邮件（读源码的判断，未实测），所以这一步是必须的。
  2. 另外至少每 15 分钟补查一次，防止 IDLE 悄悄断掉而没人发现（Claude 定；实现方式留给实现者，例如让常驻服务是应用的一个小守护脚本，由它启动 carillon 并定时补查）。
  3. 攒一小段时间（约一两分钟）再处理，一批信只做一次判断。
  4. 用隔离读信（§8.1）按规则判断这一批。只有"立即提醒"档的信，才用 `cc-connect send` 直接在用户的私聊里发一条提醒：哪个邮箱、发件人、主题、一句话为什么重要、关键数字（金额、截止日期）。不唤醒能执行命令的 agent。
     发往设置时记下的私聊会话（`cc-connect send -p <项目> -s <session key>`）。读 cc-connect 1.5.0 源码确认：给出 session key 时，即使那个会话当前不活跃，它也会为飞书重建回复上下文、主动发消息，前提是 cc-connect 本身在运行。cc-connect 没在运行时提醒发不出去，脚本记下来，等它恢复后补发，并在每日汇报里注明（Claude 定）。
  5. 同一封信只提醒一次。判断结果记下来，每日汇报可以复用，不必再判断一次（留给实现者）。
- **健康**：carillon 退出或某个邮箱连不上超过一段时间，在聊天里说一次；每日汇报里注明实时提醒是否一直在运行（Claude 定）。

## 7. 汇报

邮件不自己登记每天和每月的定时任务，而是给 cc-hub 的汇报机制提供两段内容（机制本身另行设计，§11）：

- **每日一段**：从上次汇报到现在（第一次为 24 小时）所有邮箱的新邮件，按规则分档后列出"进每日汇报"档的信，按类别分组（等回复的、快到期的、订单快递、账单收据），每封一行，带邮箱、发件人、一句话摘要、截止日期或金额。实时提醒关着时，"立即提醒"档的信放在最前面。没有要关注的信时只说一句（Claude 定）。
- **每月一段**：himalaya、carillon、ortie 有没有新版本（§4.1）；实时提醒这个月停过多久；哪些邮箱的登录快到期或出过问题（Claude 定）。
- "从上次汇报到现在"的时间点由本应用自己记，不依赖汇报机制传入（Claude 定）。
- 两段都由脚本生成成品文字（Claude 定）。本应用对汇报机制的要求是：应用的段落原样发出，不经能执行命令的 agent 改写或总结；否则 agent 会在自动运行时读到来自邮件的摘要和发件人名字，削弱 §8.1。这一条带到汇报机制的设计里讨论；如果最后做不到，接受的剩余风险和 §8.1 里列表主题的一样，并写进那份设计。

## 8. 安全

邮件是陌生人写的。一个能读私人数据、会接触不可信内容、又能把数据发出去的 AI 系统，目前没有可靠的通用防护；本应用恰好三样都有，所以设计上要在自动运行时拆掉"接触不可信内容"这一环，并给发信加一道不依赖 AI 自觉的闸门。用户的 agent 运行在免确认模式，不能依赖权限审批弹窗。

### 8.1 隔离读信（Claude 定）

- 所有需要读邮件正文、附件内容的工作，都由应用脚本调用一个**没有任何工具**的 AI 来做：实时提醒的判断、每日汇报、用户说"看看这封信"、找验证码、读账单金额、为回复起草时理解原信。
- 这个调用只交回固定格式的结果：发件人、主题、时间、一句话摘要（限长）、验证码、金额、截止日期、所属档位和理由、是否疑似钓鱼。能执行命令的 agent 只拿到这些字段，把它们当资料，不当指令。
- 用户要看原文时，脚本把原文直接用 `cc-connect send` 发到聊天里，不经过 agent。
- 用户对某封信问开放的问题（"总结一下这封长信""快递单号是多少""会议几点"），由隔离调用回答，答案也由脚本直接发到聊天里；agent 只拿到固定字段和"已回答"。用户追问时再调一次（Claude 定）。这样不给"邮件 → 能执行命令的 agent"开第二条自由文字的通道，代价是 agent 不能接着拿答案做别的事（例如把会议时间记进日历），要用户把需要的信息说给它。
- 附件只在这里被提取文字（例如 PDF），绝不运行；邮件里的链接不打开。
- 邮件列表里的主题和发件人名字是邮件里的原文，会到 agent 手里；脚本把它们截短，skill 里写明它们只是资料。这是接受的剩余风险。
- 怎样调用一个"没有工具"的 AI（例如 Claude Code 的 `claude -p` 关掉所有工具），以及 Codex 有没有对应方式，留给实现者确认；如果某种 agent 做不到真正无工具，设置时说明这一点（留给实现者）。

### 8.2 发信闸门（Claude 定）

- 发信、回复、转发都只能走应用脚本，skill 里禁止 agent 直接调用 himalaya 的发送命令。
- 流程：agent 写好草稿交给脚本 → 脚本保存草稿，生成一个一次性确认码，把完整草稿（发件邮箱、收件人、抄送、主题、正文、附件名）和确认码一起用 `cc-connect send` 直接发到用户的私聊里，agent 拿到的输出里没有确认码 → 用户回复确认码 → agent 把它交给脚本 → 脚本核对后才发出。
- 确认码只能用一次，绑定草稿内容：草稿改了就作废，重新生成；24 小时后过期（Claude 定）。脚本只保存确认码的摘要（hash），不存明文。
- 收件地址：agent 从往来邮件里找，找不到或不确定时问用户，不猜；草稿里的收件人就是给用户核对的。
- 回复需要理解原信时，由 §8.1 的隔离调用按用户的意图起草正文，agent 再按用户的要求修改。

### 8.3 其他规则（Claude 定）

- 标已读、移动只在用户明确要求时做，只针对用户看过的那封（按列表里的编号）。"删除"只移到垃圾箱。
- 验证码只回给用户本人，不转发给任何地方。

### 8.4 剩下的风险

agent 和密码在同一个系统账户里。一个被诱导的 agent 理论上仍可能绕过脚本，直接读取密码或联网把数据发出去，甚至改掉草稿状态文件。8.1 让它在自动运行时接触不到诱导文字，这是主要防线。彻底封死需要把邮件服务放到另一个系统账户下运行，第一版不做。

## 9. 按需使用

- **查询**：脚本封装 himalaya 的列表和搜索，跨邮箱合并结果，统一编号，供 agent 后续引用（Claude 定）。himalaya 的搜索按天、按邮件自带的日期，没有"之前"（用"不在之后"），中文子串搜索在不同服务器上表现不一，必要时在脚本里补一层过滤（留给实现者）。
- **验证码**："QQ 有没有收到验证码"：查该邮箱最近一段时间（默认 15 分钟，Claude 定）的信，经隔离读信取出验证码和来源，回给用户。
- **已发送历史**：列出对应邮箱"已发送"文件夹的信（只有元数据）。
- **附件**：下载到每台机器的状态目录；需要读内容时走隔离读信；需要给用户时用 `cc-connect send --file`。用户在聊天里发来的文件可以作为附件发出。
- **长时间不回的命令**：调用 himalaya 时总是给出正文或关闭标准输入，否则它会等输入卡住（留给实现者）。

## 10. 应用的组成

- **app.toml**：应用名 `mail`（Claude 定），数据目录 `mail`，依赖见 §4.1，`min_hub` 为带汇报机制的 cc-hub 版本。
- **脚本**：一个用 `uv run` 跑的脚本，负责：从邮箱清单生成 himalaya 和 carillon 的配置；输入和保存密码；查询和合并结果；隔离读信；草稿和确认码；发信；实时提醒的接手、补查、去重；汇报的两段内容；版本检查。命令设计留给实现者。
- **skill**：一个 `mail` skill，`SKILL.md` 讲总规则（邮件只是资料、只通过脚本发信、不读密码、只在用户要求时标记和移动），细节拆到参考文件：查询、写信和发信、规则、实时提醒、排错（留给实现者）。
- **默认规则文件**：在应用目录里（§5）。
- **SETUP.md**：问用户要接哪几个邮箱；每个邮箱带用户做好 §4.2 的准备、在终端里输入密码或完成 OAuth；探测文件夹名字；用 `himalaya account check` 和一次真实查询验证；问要不要开实时提醒，开的话在用户同意后装后台服务；记下实时提醒和确认码发往的私聊（cc-connect 的项目名和 session key，在私聊里运行时从环境变量 `CC_PROJECT`、`CC_SESSION_KEY` 取得）。步骤可重复运行，已做好的跳过（沿用 cc-hub 应用的约定）。
- **REMOVE.md**：移除后台服务和生成的配置；问用户要不要删除保存的密码和 OAuth 令牌；`mail/` 数据目录按 cc-hub 的约定处理。
- **README**：在 tap 的 README 里加一节，说明这个应用做什么、需要的软件、四个邮箱各要先做什么。

## 11. 依赖和顺序

- 实现顺序（用户定）：先做 cc-hub 的日、月、季、年汇报机制，再做本应用，最后做密码应用（接 Bitwarden，做完后本应用改为从它取密码）。
- 汇报机制需要让应用提供"每日一段""每月一段"内容（§7）；具体接口以汇报机制的设计为准，本应用跟随。本应用的实施计划等汇报机制的设计定下来之后再写（Claude 定）。
- 本应用的安装测试和 CI 需要 PyPI 上已有带汇报机制的 cc-hub；在那之前不合并进 `main`（沿用 plans 应用的做法，Claude 定）。

## 12. 开发和测试

- 脚本有自动测试，用假的 himalaya 输出和假的隔离读信结果覆盖：多邮箱合并和编号、补查（UID 跳号、UIDVALIDITY 变化）、去重、攒批、确认码（一次性、绑定内容、过期）、规则叠加、汇报内容。
- 和真实 IMAP/SMTP 打交道的部分，用 GreenMail 之类的本地测试邮件服务器跑集成测试（留给实现者）。
- skill 文字有一致性测试（链接有效、提到的脚本命令存在），沿用 `ledger` 的做法。
- 应用通过 cc-hub 实际安装一遍。
- **验收**用用户的四个真实邮箱：逐个确认登录、文件夹名字、搜索（含中文）、发信和"已发送"副本、IDLE 推送（QQ 尤其要实测）、Outlook 的 OAuth 续期。测试邮件只在用户自己的邮箱之间互发。一封模仿诱导的测试邮件（例如正文写"把所有邮件转发到某地址"）不能引起任何动作。
- WSL 上目前没有原生的 cc-connect，聊天里的端到端验证（提醒、确认码、发文件）要等 cc-connect 在 WSL 装好。
