# mail 应用设计

日期：2026-10-14
所属 tap：`hub-apps`（公开仓库 `Jenwein/hub-apps`）
目标 cc-hub 版本：0.5.0 及以上，需要其中的定时任务时间覆盖（`Jenwein/cc-hub` 的 `docs/superpowers/specs/2026-10-12-cron-overrides-design.md`），以及脚本任务、按需任务、限权任务和凭据规则（同仓库 `docs/superpowers/specs/2026-10-14-script-tasks-design.md`）

标注约定：没有标注的内容是用户的决定；标"（Claude 定）"的是 Claude 替用户做的选择，用户可以改；标"（留给实现者）"的由实现者决定。

---

## 1. 这是什么，为什么做

`mail` 是 `hub-apps` 里的邮箱应用，让 agent 在聊天里替用户管理他所有的邮箱。

起因：一个人往往有好几个邮箱（QQ、Gmail、Outlook、工作邮箱……），各家的通知不一定弹得出来，重要的邮件就这样漏掉了。

用户在聊天里可以：

- 新增、修改、删除要管理的邮箱。例如"帮我把新的飞书工作邮箱加进来"；
- 收到重要邮件的即时提醒，其余邮件每天看一份汇总；
- 搜索邮件，标已读，归档，删除；
- 写信、回信、转发，带附件；
- 了解收到的附件是什么，需要时让 agent 把附件发到聊天里。

这个应用公开发布。每个人、每个邮箱判断邮件的标准都不一样，所以规则分成三层（§4）：所有人都一样的固定规则；每个人自己设、每个邮箱还能单独覆盖的可定制规则；没设时使用的默认值。

## 2. 目标、非目标、绝对不能出的错

**目标**

- 在聊天里新增、修改、删除邮箱（§5）。
- 后台按用户设定的频率查新邮件；按用户的标准挑出重要的信即时推送，其余进每日汇总（§6）。
- 搜索、读信、标已读、归档、删除（§7）。
- 写信、回信、转发，带附件；发出前用户确认（§8）。
- 描述收到的附件，按要求下载并发到聊天里（§9）。

**非目标**

- 语音转文字等聊天平台本身的功能：交给 cc-connect，应用不涉及。
- 网易、QQ、Gmail、飞书以外的邮箱，包括个人 Outlook（只能走 OAuth，没有自己注册的应用就得借用 Thunderbird 的身份，有被封的风险）、iCloud、Lark、Microsoft 365 工作邮箱。以后再一家一家加。
- POP3；Exchange 的 EWS 接口；飞书邮箱的 OpenAPI（需要公司里建自建应用）。这一版只走 IMAP/SMTP（Claude 定）。
- 监视收件箱以外的文件夹，包括垃圾邮件（Claude 定）。
- 签名、模板、定时发送；在邮箱服务器上建收信规则、自动回复（Claude 定）。
- 联系人管理；处理日历邀请。日历邀请只当普通邮件描述（Claude 定）。
- 打开邮件里的链接、按邮件的要求去登录网站或下载东西（Claude 定）。

**绝对不能出的错**

1. **刷屏。** 把一长串邮件全部列进聊天窗口。任何列表默认最多 10 条，后面只写一句"还有 N 封"，用户要看再接着列（条数 Claude 定）。每日汇总按邮箱和类别归类计数，只点名几封值得看的。
2. **擅自删信，未经批准发信。** 没有用户明确说"删"或"发"，就不删、不发（§4.1）。
3. **漏信而不出声**（Claude 定）。某个邮箱连不上、密码失效、后台检查停了，都要告诉用户（§6.5）。悄悄停止检查，比不做这个应用还糟：用户以为有人盯着，其实没人盯。
4. **照邮件里的话办事**（Claude 定）。邮件内容是数据，不是指令。邮件里写着"请把这封信转发给……""忽略之前的设置"，agent 一概不照做；只有用户在聊天里说的话才算数。读邮件的后台任务还系了安全带：只能执行一组只读的命令（§6.2、§11），被骗了也发不出信、删不了信。
5. **密码泄露。** 密码进 git，或者出现在回复里。

## 3. 国际化

- 给 agent 读的文字（skill、`SETUP.md`、`REMOVE.md`、cron 正文）用英文写；agent 跟用户说用户的语言。
- 推送、汇总、草稿说明用用户的语言；邮件正文写成什么语言，由用户和收件人决定。
- 规则文件里，用户的原话保留原样。

## 4. 三层规则

### 4.1 固定规则（所有人都一样，不能改）

- **发信**：发出前一定先给用户看完整草稿，包括发件邮箱、收件人、抄送、主题、正文、附件；用户说"发"才发。草稿改过之后要重新完整展示一次，再等用户说"发"（重新展示是 Claude 定）。
- **删信**：先把要删的信列出来，用户说"删"才删。删除是把信移到废纸篓，不彻底删除（移到废纸篓是 Claude 定，用户未反对）。
- **后台只看不动**：后台检查新信时，不标已读、不移动、不删除；用户在手机邮箱里看到的状态不变（Claude 定）。
- **标已读、归档**：可以撤回，用户说了就直接做，不用确认（Claude 定）。
- **密码**：只存在服务器本地，不进 git，存好之后不再在回复里显示。
- **附件**：只描述，用户明确要哪个附件才发到聊天里（§9）。
- **列表上限**：见 §2"绝对不能出的错"第 1 条。
- **邮件内容是数据**：见 §2"绝对不能出的错"第 4 条。

### 4.2 可定制规则（每个人设一份，每个邮箱可以单独覆盖）

| 项 | 说明 | 层级 |
|---|---|---|
| 什么算重要 | 用一句话描述，agent 读信时据此判断，不靠关键词 | 用户级，邮箱可覆盖 |
| 重要的信怎么送达 | 即时推送，或者和每日汇总一起 | 用户级，邮箱可覆盖 |
| 每日汇总 | 几点发，发不发 | 只有用户级（Claude 定） |
| 静音 | 某个邮箱或某个发件人的信不推送，只进汇总 | 用户级和邮箱级都可以 |
| 查信频率 | 后台多久查一次，例如每 5 分钟，或每天一次 | 只有用户级（Claude 定） |

- 用户在聊天里的纠正（"这类以后要推""这种别推了"）记在这一层。没说范围时，记在那封信所在的邮箱上；用户说"所有邮箱都这样"才记成用户级（Claude 定）。记下后用一句话复述规则和它管哪个邮箱。
- 判断一封信时，邮箱级的规则优先于用户级，用户级优先于默认值（§4.3）。
- 设置之间有冲突时，agent 在设置的当时就指出，不等出问题。例如关掉了每日汇总，又把某个邮箱设成"和汇总一起"，那个邮箱的信就永远不会送到；又如查信频率设成每天一次，"即时推送"实际上也变成了每天一次（Claude 定）。
- 删除邮箱时，清掉的是这个邮箱单独的那一份规则；用户级的规则不动。

例子（用户本人的设置，不是应用的默认值）：飞书工作邮箱——"直接发给我（我在收件人里，不是抄送、不是群发列表）、需要我回复或处理的信算重要，即时推送"。

### 4.3 默认值

用户什么都没设时使用（全部 Claude 定）：

- 算重要的信：需要用户本人回复或处理的信，以及跟钱、账户安全有关的信（账单、扣款、异地登录提醒）；
- 重要的信即时推送；
- 每日汇总每天早上 8 点发，用用户所在地的时间；
- 每 5 分钟查一次新信。

加第一个邮箱时，agent 把这套默认值告诉用户，问一次要不要改。之后再加邮箱时，问一句这个邮箱要不要单独的规则（Claude 定）。

## 5. 管理邮箱

### 5.1 新增

1. 用户说"把我的 XX 邮箱加进来"，给出邮箱地址。
2. agent 认出是哪家：先看地址的域名；公司自己的域名（飞书工作邮箱通常是这样）就查域名的 MX 记录；还认不出就问用户（查 MX 记录是 Claude 定）。
3. agent 告诉用户在这家的设置里去哪儿打开第三方客户端、生成专用密码或授权码。每家的步骤写在应用里的一份指南里，跟记账应用的 `sources/` 一样，一家一个文件。第一版只支持四家：网易（163、126，yeah.net 同属网易，一并支持，Claude 定）、QQ、Gmail、飞书。其他邮箱以后再一家一家加；每家一份指南、一组服务器设置，加一家不需要改动别的部分。用户要加一个还不支持的邮箱时，agent 直接说明暂不支持。
   - **飞书**（2026-10 查到的官方说法，用户已在自己的飞书上核对过）：专用密码只能在飞书**桌面端**生成，路径是：头像 → 设置 → 邮箱 → 第三方邮箱客户端登录 → 进入设置 → 选设备 → 生成。前提是公司管理员已经在管理后台打开这个功能，路径是：产品设置 → 邮箱 → 邮箱管理工具 → 用户功能权限 → 第三方邮箱客户端。从文档的说法看，默认很可能是关的。生成专用密码的页面上同时列出了邮箱地址和服务器设置：`imap.feishu.cn:993`、`smtp.feishu.cn:465`，都用 SSL。通过第三方客户端发的单封信最大 36MB。看不到"第三方邮箱客户端登录"这个入口，就说明管理员没开，agent 告诉用户去找公司的飞书管理员。
4. 用户在聊天里把专用密码发给 agent。
5. 服务器设置 agent 自己填，然后实际登录一次收信服务器、一次发信服务器。只验证能登录，不发测试信，免得工作邮箱里多出垃圾邮件。两边都通过才算加好；失败就告诉用户卡在哪一步、该去找谁。
6. 密码存进服务器本地的密钥文件（§10），不进 git，之后的回复里也不再显示。存好后提醒用户把聊天里发密码的那条消息撤回（cc-hub 0.5.0 的凭据规则允许 agent 这样保存用户交给它的凭据）。
7. 给邮箱起一个短名，例如"工作""QQ"。之后用户说"用工作邮箱回他"，agent 就知道用哪个。
8. 建立本地索引（§7.1）。加邮箱之前已经在收件箱里的信不推送，也不进汇总，只有之后新到的信才算新信（Claude 定）。不这样的话，第一次检查就会把几百封旧信当新信处理，直接刷屏。
9. 规则：第一个邮箱问一次默认值，之后的邮箱问一句要不要单独的规则（§4.3）。

### 5.2 修改（Claude 定，用户未反对）

- 专用密码过期或重新生成了，换一个新的（同样在聊天里发，换好后重新登录验证）；
- 改短名；
- 改这个邮箱的可定制规则（§4.2）；
- 暂停提醒：邮箱仍然在管理范围内，信只进汇总。

### 5.3 删除

- 以后不再管这个邮箱：存着的密码当场删掉，这个邮箱单独的规则清掉。
- 之前从这个邮箱下载的附件**留着**。
- 本地索引里这个邮箱的记录删掉（Claude 定）。
- 删之前，agent 用一句话说明会删什么、留什么，用户确认后再删（Claude 定）。

## 6. 收信、提醒、汇总

### 6.1 后台检查（脚本任务 `poll`）

- 按查信频率（默认每 5 分钟，用户可以改，§4.2）执行 `mk` 的检查命令，不唤醒 agent。
- 对每个邮箱的收件箱，只取上次之后新到的信，存进本地索引。只读取，不改变信在服务器上的状态（§4.1）。
- 能用固定条件判断的先由脚本处理：被静音的邮箱或发件人的信，以及送达方式是"和汇总一起"的邮箱的信，直接记为进汇总（Claude 定）。
- 其余的新信记为待判断。有待判断的信时，执行 `cc-hub cron wake mail/triage` 唤醒 agent，一批只唤醒一次。
- 用量：每次检查只要发现需要判断的新信，就唤醒一次 agent。按默认的每 5 分钟一次，一个普通的收件箱估计一天几十次，最多 288 次。查信频率就是这个用量的上限，嫌多就把频率调低；用户的纠正记成"某发件人别推了"之后，这个发件人的信由脚本直接分走，不再唤醒 agent（Claude 定）。
- 唤醒之后，这一批要等 agent 处理完并标记才算结束。约 10 分钟内还没处理完（例如 agent 那次运行失败），下一次检查再唤醒一次；还没超时的不重复唤醒（Claude 定，具体时长留给实现者）。查信频率很低（例如每天一次）时，重试要等到下一次检查；但每日汇总会先判断所有还没判断的信，重要的放在汇总最前面，所以一次唤醒失败最晚在下一份汇总里补上（Claude 定）。

### 6.2 判断和推送（按需任务 `triage`）

- agent 读这一批待判断的信（数量有上限，分批处理），按 §4 的规则逐封判断：重要的推送，其余进汇总。
- 拿不准的按重要处理，宁可多推，因为漏掉重要邮件正是这个应用要解决的问题（Claude 定）。
- 一批只发一条消息。每封重要的信写：哪个邮箱、谁发的、主题、要用户做什么、有没有截止时间、附件（文件名和大概内容，§9）。超过 10 封时只列 10 封，后面写"还有 N 封"（格式 Claude 定）。
- 没有重要的信就什么都不发（回复 `NO_REPLY`）。
- 处理完调用 `mk` 标记这一批已处理。
- 在单独的会话里运行（`session: new_per_run`），不占用户正在聊的会话（Claude 定）。cc-connect 的提示词任务如果跑在用户的会话里，用户正聊着时任务会撞车失败。
- 安全带：`triage` 是限权任务，`allow` 里只有 `mk` 的后台命令组（§11）。这组命令只读邮件、读写本地状态，没有发信、删信、移动、改标记的能力。即使用户平时用 YOLO 模式，这个任务也只能执行这组命令。

### 6.3 接着推送说话

推送之后用户直接回一句"回他：好的，周三可以"，agent 知道说的是刚推的那封。

实现方式（Claude 定）：推送记录在本地，用户聊天的那个会话看不到推送任务的上下文，所以 agent 遇到"回他""那封信"这类说法时，先查最近推送的记录；只有一封对得上就用它，有几封都可能时，列出来问是哪封。用户在飞书里引用回复推送消息时，cc-connect 会把被引用的内容带进提示词，可以直接用。

### 6.4 每日汇总（提示词任务 `digest`）

- 默认每天 08:00，用户可以改时间或关掉（`cc-hub cron set mail/digest …`）。登记为静默（`silent: true`），聊天里不出现"⏰"开始提示。
- 时间按服务器的时区执行。`SETUP.md` 比较服务器时区和用户所在地；不一致时告诉用户，并把用户说的时间换算成服务器时间再写进设置。用户所在地有夏令时的话，提醒他汇总时间每年会两次差一小时（Claude 定）。
- 先执行一次检查，保证汇总包含最新的信；再像 `triage` 一样判断所有还没判断的信，重要的放在汇总最前面（Claude 定）。
- 内容：上次汇总之后、没有推送过的信，按邮箱分组，每组按类别计数（例如"推广 12、通知 5、其他 3"）；点名最多 5 封值得看的（Claude 定）；最后列出邮箱的问题（§6.5）。类别由 agent 判断，类别名用用户的语言（Claude 定）。
- 没有新信也发一行"昨天没有新邮件"，让用户知道检查还在运行（Claude 定）。
- 在单独的会话里运行；和 `triage` 一样是限权任务，只能执行 `mk` 的后台命令组。

### 6.5 连不上的邮箱

- 检查时某个邮箱登录失败、密码失效、服务器连不上，脚本记下来。
- 同一个邮箱的同一个问题，第一次出现时唤醒 `triage` 告诉用户，之后每天最多再提一次（在汇总里）。恢复后在下一条消息里说一句已恢复（Claude 定）。
- 告诉用户时说清是哪个邮箱、什么问题、怎么修。例如"QQ 邮箱的授权码失效了，去 QQ 邮箱设置里重新生成，再发给我"。

**检查本身停了**（Claude 定）。最可能的故障是后台检查根本没在跑：守护进程的 PATH 里找不到 `uv`，任务被删掉了，或者 cc-connect 没在运行。静音的脚本没法报告自己没运行，所以从三个地方补上：

- `SETUP.md` 登记 `poll` 之后，等到它第一次真正跑完（看检查状态里的时间）才算设置完成；没跑起来就排查，常见原因是 PATH。
- 每日汇总先看上一次检查成功是什么时候，太久没成功就写在汇总最前面。汇总自己会现查一次，但不能用这次现查掩盖后台检查停了的事实。
- 用户在聊天里提到邮件时，mail skill 也先看一眼上一次检查的时间，太久就先说这件事。

"太久"的界限：两个检查间隔再加 10 分钟（具体数值留给实现者）。

## 7. 用户开口时做的事

### 7.1 搜索

- 在所有邮箱或用户指定的邮箱里，按发件人、主题、时间、内容找信。
- QQ、163 等邮箱的服务器不支持中文搜索，所以搜索用本地索引：加邮箱时导入最近一段时间的信（Claude 定：至少最近 90 天；范围留给实现者），之后由后台检查持续补进来。索引存信封信息和纯文本正文，不进 git（§10）。
- 本地索引覆盖不到的更早的信，用服务器搜索补；服务器不支持中文、搜不到时，如实告诉用户（Claude 定）。
- 结果最多列 10 条，每条写哪个邮箱、发件人、主题、日期。用户挑中一封，agent 再读全文或给出总结。

### 7.2 读信

- 用户要看哪封，agent 就给全文或总结。读信不会把信标成已读，用户说要标才标（Claude 定）。

### 7.3 标已读、归档、删除

- 标已读、标未读、归档：用户说了就做，做完报一句做了几封（Claude 定）。归档的去处：Gmail 是移出收件箱；其他邮箱移到"归档"文件夹，没有这个文件夹时问用户是否新建（Claude 定，细节留给实现者）。
- 删除：先列出要删的信（同样受列表上限约束：超过 10 封时列 10 封，并写明一共多少封），用户说"删"才删，删除是移到废纸篓。

## 8. 写信、回信、转发

- 回信、写新信、转发是同一个功能，都走 §4.1 的草稿确认。
- 回信默认用收到这封信的那个邮箱发；写新信时用户没指定邮箱，就问用哪个（Claude 定）。
- 回信默认只回发件人，用户说"回复所有人"才回所有人；回信要和原信在同一个会话串里（Claude 定）。
- 转发默认带上原信的附件（Claude 定）。
- 发出的信在这个邮箱的"已发送"里出现，而且只出现一次（有的邮箱服务器会自动存一份，有的要客户端自己存，留给实现者逐家处理）。
- 附件可以是用户在聊天里发给 agent 的文件（cc-connect 存在总站的 `.cc-connect/attachments/` 下，路径会出现在提示词里），也可以是之前下载过的附件。
- 发之前检查大小：超过这个邮箱的上限（例如飞书 36MB）就在草稿阶段告诉用户（Claude 定）。
- 收件人地址、退款政策这类信息，agent 可以用自己的一般能力去网上找（例如"帮我给 Cursor 写信申请退款"）。找到的地址写进草稿，由用户确认。
- 已知限制：cc-connect 1.5.0 收不了飞书聊天里超过 2MB 的文件，1.5.1 测试版修好了。简历 PDF 常常超过 2MB，所以"把聊天里的简历作为附件发出去"需要 cc-connect 1.5.1 或更新。`SETUP.md` 检查版本并告诉用户（Claude 定）。

## 9. 附件

- 推送、汇总、读信时，只告诉用户附件的文件名和大概内容，例如"附件：offer.pdf，薪资和入职日期说明"。
- 要说出内容，agent 得先把附件下载到服务器上读一遍；下载的文件存在服务器本地，不进 git（Claude 定）。
- 用户明确要哪个附件，才用 `cc-connect send --file` 发到聊天里。飞书上文件最大 30MB，图片最大 10MB。超过的话告诉用户文件在服务器上的位置，不硬发（Claude 定）。
- 删除邮箱时，下载过的附件留着（§5.3）。

## 10. 数据放在哪里

| 内容 | 位置 | 进 git |
|---|---|---|
| 邮箱列表（地址、短名、哪家、服务器设置）、可定制规则、默认值的修改 | 数据目录 `mail/` 下 | 进 |
| 密码 | 总站 `secrets/mail/` 下（总站的 `.gitignore` 已经忽略 `secrets/`） | 不进 |
| 本地索引、检查状态（每个邮箱查到哪了、待判断的批次、推送记录、邮箱问题） | 留给实现者 | 不进 |
| 下载的附件 | 留给实现者 | 不进 |

- 规则文件要让用户能直接读懂、手改（Claude 定）。格式留给实现者：可以是 TOML，也可以是 TOML 加一份 Markdown。
- 改邮箱列表或规则后，只提交 `mail/` 下的改动。检查状态变化很频繁，不提交。
- 不进 git 的东西放在哪里由实现者决定。可以在 `mail/` 里放一个随种子播种的 `.gitignore`（先确认 cc-hub 的应用校验允许这个文件名），也可以放在总站之外；无论放哪里，`REMOVE.md` 和 skill 都要能告诉用户在哪里。
- 换机器（cc-hub §8.8）时，本地索引在新机器上重建；附件不会跟过去，`REMOVE.md` 和文档里写明这一点（Claude 定）。

## 11. 收发信工具 `mk`

自己写一个 Python 命令行工具，`uv run apps/mail/scripts/mk.py` 运行，和记账应用的 `lk` 一样（Claude 定）。不用 himalaya 的原因（2026-10 调研）：

- himalaya 几周就出一个版本，JSON 输出格式在版本之间一直在变（下一版又要改 `message read --json`），163/126 需要的 IMAP `ID` 修复还没发布；
- 国内邮箱的服务器都不支持中文搜索，用哪个工具都得自己建本地索引；
- 自己写的工具能把这个应用的固定规则做进工具本身（见下面"安全"）。

要求：

- 后台检查和 agent 用同一个工具；输出 JSON，字段由这个应用自己定、有测试守着；所有列表类输出都分页，默认一页 10 条。
- 要处理的各家差异（已知的）：163/126 登录后要先发 IMAP `ID` 命令；QQ 企业邮的 UID 取法；GBK/GB18030 编码的信；RFC 2231 编码的中文附件名；回信的会话串头部；"已发送"的保存；没有 MOVE 命令时用复制加删除标记实现移动。
- **后台命令组**：给限权任务（`triage`、`digest`）用的一组命令，放在同一个子命令下（例如 `mk.py bg …`），以便权限清单用一个前缀放行。组里只有：检查、列出和标记待判断的批次、读信、搜索、推送记录、邮箱问题列表。组里没有任何发信、删信、移动、改标记、改设置的命令，也不能读密码。限权任务的命令里不能有 `;`、`|` 这类接续符号，所以每次调用只能是一条 `mk.py bg …` 命令，参数里也不要求用到这些符号。
- **安全**（Claude 定）：
  - 发信只能发一份已经保存的草稿，草稿内容在展示给用户之后改过的，工具拒绝发送；
  - 删除只接受一次列出的结果；
  - 后台检查的命令不带任何改变服务器状态的操作。
- 第三方库的选择留给实现者（调研时的候选：`imap-tools`、标准库的 `smtplib` 和 `email`）。
- 命令的具体名字和参数留给实现者。需要覆盖的功能：邮箱的新增、验证、修改、删除；检查；列出和标记待判断的批次；最近推送的记录；搜索；读信；标记；移动和归档；删除；草稿、展示和发送；附件下载；邮箱问题列表。

## 12. 应用的组成

```
mail/
├── app.toml            min_hub = "0.5.0"，data dirs = ["mail"]，requires 至少有 uv
├── SETUP.md
├── REMOVE.md
├── skills/mail/        SKILL.md 和按主题拆开的说明（管理邮箱、收信与规则、搜索与操作、写信、附件）
│   └── providers/      每家邮箱一份接入指南（§5.1）
├── cron/
│   ├── poll.md         脚本任务，*/5 * * * *，exec: uv run apps/mail/scripts/mk.py poll
│   ├── triage.md       按需任务，session: new_per_run，allow: mk 的后台命令组
│   └── digest.md       提示词任务，0 8 * * *，session: new_per_run，silent: true，allow: mk 的后台命令组
├── scripts/            mk.py 和它的包
└── seed/mail/          配置骨架
```

**SETUP.md**（每一步先检查再做，可以重跑）：

1. 检查 cc-connect 的版本，低于 1.5.1 时告诉用户：从聊天里发给 agent 的超过 2MB 的文件收不到（§8）。
2. 讲一遍默认值（§4.3），问要不要改。查信频率和汇总时间用 `cc-hub cron set` 写进总站设置。
3. 加第一个邮箱（§5.1）。
4. 登记定时任务时，`poll` 是脚本任务，按 cc-hub 的规定先把命令告诉用户、得到同意再登记。用户不同意，就告诉用户：没有后台检查，就没有即时推送，每日汇总也只能在汇总时现查（Claude 定）。

**REMOVE.md**：告诉用户 `mail/`、密钥、本地索引和附件各在哪里；问用户要不要删掉 `secrets/mail/` 下的密码和令牌，用户同意才删（Claude 定）。定时任务由 `hub-apps` 注销。

## 14. 测试

- `mk` 对着本地的 IMAP/SMTP 测试服务器跑完整流程：加邮箱、检查、搜索、标记、归档、删除到废纸篓、草稿和发送、附件上传和下载（测试服务器的选择留给实现者）。
- 各家差异用录下来的样本做单元测试：GBK 编码的信、RFC 2231 附件名、163 的 `ID` 命令、没有 MOVE 时的移动。
- JSON 输出的契约测试；列表分页上限。
- 安全规则：后台命令组里没有会改变服务器状态或发出东西的命令；改过的草稿拒绝发送；后台检查不改变服务器状态（在测试服务器上对比检查前后的标记）；密码不出现在任何输出和 git 里。
- 检查状态：新加的邮箱不把旧信当新信；唤醒后没处理完的批次按时重新唤醒，没超时的不重复唤醒；连不上的邮箱只报一次。
- 手工验收：用真实的 QQ 邮箱和飞书工作邮箱走一遍 §5、§6、§7、§8、§9，在飞书聊天里收推送、回"回他：…"、看汇总。验收在用户的 WSL 上做，在那里装好 cc-connect（1.5.1 或更新）、作为 systemd 用户服务运行，是验收计划的一部分（Claude 定）。
