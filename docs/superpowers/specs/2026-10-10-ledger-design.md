# ledger 应用设计

日期：2026-10-10
所属 tap：`hub-apps`（本仓库，本地 `C:\dev\hub-apps`，之后发布为公开的 `Jenwein/hub-apps`）
目标 cc-hub 版本：0.4.0 及以上

标注约定：没有标注的内容是用户的决定；标"（Claude 定）"的是 Claude 替用户做的选择，用户可以改；标"（留给实现者）"的由实现者决定。

## 1. 这是什么，为什么做

用户把 cc-hub 总站放在自己的 Linux 服务器上，通过聊天（cc-connect 接飞书等 bot）让 agent 替自己做事。cc-hub 只提供应用机制，本身不带任何应用；记账、机器管理、项目管理这些能力，都以应用的形式放进用户自己的 tap 仓库 `hub-apps`。`ledger` 是这个仓库里的第一个应用。

`ledger` 让 agent 用 [beancount](https://github.com/beancount/beancount)（纯文本复式记账）替用户记账，并用 [Fava](https://github.com/beancount/fava) 提供网页版报表。用户主要通过聊天使用它：随口记一笔、问账、发账单文件让 agent 导入、让 bot 发图表；要看完整报表时再打开 Fava。

这个应用会公开发布，任何 cc-hub 用户都能装，所以它按国际化来做（§3）。用户本人在中国，第一批要支持的账单来源都是国内的。

## 2. 目标、非目标、绝对不能出的错

**目标**

- 聊天里记账：用户说一句，agent 直接记进账本，再把记成的分录回给用户看；用户说"改一下"就改。
- 导入账单：用户把支付宝、微信、美团、京东和各家银行导出的账单文件发到聊天里，agent 导入，不重复、不漏记，拿不准的问用户。
- 问账：任何关于账本的问题在聊天里直接回答。
- 图表：在聊天里按要求发图；每月小结附图。
- Fava：常驻运行，经 SSH 隧道在电脑上看，经 Tailscale 在手机上看。
- 账本覆盖：日常收支、银行卡、支付宝和微信的各个子账户、信用卡和花呗、股票基金（含每日价格）、借出和借入、报销。

**非目标**

- 从用户现有的 SQLite 记账程序迁移旧账。这是用户自己总站里的一次性工作，不进应用，以后另做。
- 给 double-entry-generator 上游补更多银行的支持。这是以后的方向。
- 抓取淘宝、拼多多、抖音的订单。它们没有官方导出，消费会出现在支付宝或微信的账单里。
- 帮用户搭域名加密码的反向代理。文档里提一句，不做成设置项。
- 预算、多人共用一本账（Claude 定：这次不做）。
- 投资的进阶功能：从支付宝等账单里识别基金申购赎回并换算份额、导入券商对账单、国内基金的净值价格源。用户目前还没开始投资，以后学了再加（Claude 定）。这一版只支持 §7 的基础记法。

**绝对不能出的错**（Claude 定）

1. 金额、日期或账户记错了却没人发现。所有写入都要过 `bean-check`；账单格式交给确定性的工具解析，不靠模型猜数字。
2. 同一笔钱记两次。
3. 账本数据去到新的地方。应用不得把账本内容发给总站已经在用的渠道以外的任何服务（已经在用的渠道：用户的聊天平台、agent 本身、总站的私有 git 远程、用户自己的 Tailscale 网络）。不用在线转换网站、云端 OCR、额外的 AI 分类服务。抓价格时只发出代码，不发出持仓和金额。
4. 没经用户同意就安装软件。沿用 `hub-apps` 的规则：说明每条命令做什么，用户批准才执行。
5. 公开的 tap 仓库里出现任何真实的个人账单或账本数据。测试用的账单样例全部是合成的。

## 3. 国际化

- 应用里所有给 agent 读的文字（skill、`SETUP.md`、`REMOVE.md`、cron 提示词）用英文写。agent 跟用户说用户的语言。
- 账户名默认用英文（如 `Expenses:Food`），用户可以改。主币种在设置时问。
- 账单导入按"来源"组织（§6）：每个来源一份英文说明。先写国内这些来源；别的国家的银行以后照同样的格式补，有 double-entry-generator 支持的直接用它，没有的走 agent 读文件的路径。

## 4. 用户怎么用

这一节同时是应用 README 里"怎么用"的底稿。

**装好以后**：在聊天里说"装一下记账应用"。agent 按 `hub-apps` 先给用户看要装什么，同意后装软件、问设置（§8），然后就能用。

**平时：想记就随口说一句，不强制。**

- 用支付宝、微信、银行卡付的钱，导入账单时都会补上，所以不记也不会漏。随口记的好处是当时就知道这笔是干什么的，账也是实时的。
- 账单里查不到的必须在聊天里说：现金；导不出账单的（如抖音月付）；没有导入工具、用户又不打算导入的来源。
- 账单看不出用途的最好在聊天里说：借给别人钱（"借给张三 500"）、要报销的（"这笔打车 80 要报销"）、买卖股票基金。
- 记错了直接说"刚才那笔改成 45"。

**每月一次：导入账单。** 每月 1 号 bot 提醒。用户从各平台和银行导出上个月的账单，把文件发到聊天里。每月导一次最省事，微信一次最多只能导三个月。账单压缩包带密码的，建议用户自己解压后发里面的文件；如果用户在聊天里给了密码，agent 只用这一次，不写进任何文件。agent 导入完告诉用户新增几笔、对上几笔、还有几笔等确认。

**随时**：在聊天里问账；让 bot 发图；电脑上开 SSH 隧道看 Fava；手机上通过 Tailscale 打开 Fava。

## 5. 账本

### 5.1 数据目录

`app.toml` 声明一个数据目录 `ledger`。它属于用户，跟着总站进 git，应用升级和卸载都不碰它。初始结构由 `seed/ledger/` 播种（Claude 定，具体文件名留给实现者微调）：

```
ledger/
├── main.beancount        选项、include
├── accounts.beancount    open / commodity 指令（含投资品的价格源元数据）
├── prices.beancount      price 指令，定时任务追加
├── txns/<年>.beancount   交易，按年一个文件
├── txns/opening.beancount  期初余额
├── txns/web.beancount    在 Fava 网页上新增的分录
├── documents/            原始账单文件，按 Fava 的 documents 约定按账户存放
├── importers/            double-entry-generator 的规则文件，每个来源一份
├── inbox/                正在导入的账单、暂存分录和计划，不进 git
└── config.toml           应用设置（§8）
```

`main.beancount` 设 `operating_currency`、`option "documents"`，用 include 引入其余文件，交易文件用通配 `txns/*.beancount`（匹配不到文件会报错，`opening.beancount` 和 `web.beancount` 始终在，所以总能匹配到）。`web.beancount` 里的 Fava 选项 `insert-entry` 让网页上新增的分录写进这个文件；聊天和导入写进当年的交易文件。

### 5.2 账户结构

- 资产：每张银行卡一个账户（带银行和尾号）；支付宝余额、余额宝、微信零钱、零钱通各一个账户；现金；投资账户。
- 负债：每张信用卡、花呗、京东白条等各一个账户。
- 应收：每个借款人一个"应收"账户；报销先挂在"应收报销"上，公司打款后冲掉。
- 应付：每个债主一个"应付"账户。
- 收入：工资等；余额宝、零钱通的收益记为收入（按 §6.2 第 6 条的余额核对入账）。
- 支出：按类别分，默认一套常用类别（Claude 定，留给实现者定具体清单），用户可增改。

### 5.3 写入规则（所有写账本的地方都适用）

1. 写之前先看 `ledger/` 有没有别人留下的未提交改动（比如用户在 Fava 网页上改过）；有就先单独提交一次，再开始自己的改动（Claude 定）。
2. 写完跑 `bean-check ledger/main.beancount`，通过才算数；不通过就修好或撤回，不留半截。
3. 用 `bean-format` 保持格式整齐（留给实现者决定是否每次都格式化整个文件）。
4. 每个任务结束提交一次，只提交 `ledger/` 下的改动，提交说明写清做了什么。推送交给总站每晚的整理任务。

## 6. 导入账单

### 6.1 工具

- 能用 [double-entry-generator](https://github.com/deb-sig/double-entry-generator)（以下简称 deb，Go 写的单文件程序，持续维护）解析的来源都用它：支付宝、微信、美团、京东、建行、工行等。它按规则文件把每一笔转成 beancount 分录，规则按对方、商品、类别、支付方式匹配，能指定支出账户和"支付方式对应的账户"（`methodAccount`），也能忽略某些行。
- deb 不跨文件去重，所以去重和对账由应用自带的脚本做（§6.3）。
- deb 不支持的来源（例如宁波银行、上海银行储蓄卡）走"agent 读文件"的路径（§6.4）。
- 淘宝、拼多多、抖音不单独导入。

### 6.2 记法

1. **先导支付和平台账单，再导银行账单。** 支付宝、微信、美团、京东的账单里有"支付方式"一列。每一笔都记到实际扣款的账户上：卡尾号对应那张卡，余额对应余额账户，花呗对应花呗负债。支付宝和微信只用来看出买了什么、该归哪一类，不设中转账户。
2. **银行账单里写着支付宝、财付通、美团支付等的行**，按账户、金额、时间去对已经记过的那笔，对上就跳过，对不上的列给用户。
3. **转账只记一笔**：充值、提现、花呗还款、信用卡还款在两边账单里各出现一次，记成一笔转账，另一边对上即可。
4. **聊天里记过的那笔**也会被对上（在 Fava 上或手工加的、还没对上过账单的分录也一样）：保留用户说的用途、类别和备注；账单显示实际扣的是另一个账户时，把付款那一边的账户改过来，并补上账单里的订单号等信息。借出、报销、转账的另一边不会被改动。只有确定是同一笔钱时才自动对上，下面几条都要满足：
   - 金额相同，进出方向也相同。
   - 付款的路子对得上：分录记了付款渠道（`channel`），正是这份账单的来源，付款那一边记在这个渠道默认的账户（§8.2 第 1 步的设置）或账单上的账户上；或者这一行出自那个账户自己的银行流水（比如用户说刷卡付的，卡的流水里那一行）。用户说的是刷卡、账单却是支付宝或微信的，不自动对上。
   - 是同一类事：两边都是自己账户之间的转账（借出、还款、充值这类只涉及资产和负债账户的），或者都是收支（有支出或收入账户，还没分类的也算）。看不出是哪一类的（例如对方账户还没定的收款）不自动对上。
   - 两边都写了具体类别时，类别相同。

   好几行账单都能对上同一笔时，日期最近的那行对上；一行账单在同样近的日期上有好几笔可对时，问用户。时间窗口内金额相同或相近、却不满足这些条件的，都列给用户确认，不会当成新的一笔直接写入。
5. **分类**：规则在 `ledger/importers/` 里。遇到没有规则的新商户，agent 问用户一次，把答案补成规则。
6. **余额核对**：账单里带每行余额的，导入后在账单最后一天加一条 `balance` 断言，余额对不上 `bean-check` 就会报错。账单里没有余额的账户（支付宝余额、余额宝、微信零钱、零钱通、花呗、白条、现金），每月导完账单后 agent 问用户这些账户当前的余额（用户可以发截图），同样写成 `balance` 断言；余额宝和零钱通的差额记为收益收入（这是收益入账的方式），其他账户对不上的和用户一起查（Claude 定）。
7. **原始账单**：存进 `ledger/documents/` 对应账户的目录，Fava 里能从账户点回原始账单。
8. **记账起始日之前的行不导入**：账单里日期早于 `config.toml` 中 `[ledger] start` 的行算作跳过，导入报告里单独说明是起始日之前的；起始日当天及以前的账单余额也不写成 `balance` 断言。

### 6.3 去重和对账脚本

应用自带一个确定性的脚本（留给实现者命名和实现），输入是 deb 或 agent 生成的新分录和现有账本，输出三类：

- 新的：直接写入；
- 对上的：跳过，或按 §6.2 第 4 条修正已有分录；
- 拿不准的（多个候选、金额相近但不等等）：交给 agent 问用户。

匹配优先用账单自带的稳定编号（订单号、交易号，写进分录的元数据）；没有编号时按账户、金额和时间窗口匹配。具体的元数据键名、时间窗口、要不要复用 beangulp 的比较逻辑，留给实现者，但要用测试覆盖 §6.2 的每一种情形。

匹配的结果先写成计划文件，agent 和用户处理完拿不准的再执行。计划里记着匹配时账本的摘要（账本目录下除 `inbox/` 以外所有 `.beancount` 文件的 SHA-256）和账本的路径。执行前重新计算：账本在这之间有任何变化（聊天里新记了一笔、Fava 上改过、另一份计划已经执行），或者计划不是这本账的，就拒绝执行，要求重新匹配，这样同一笔钱不会因为过期的计划记两次。

### 6.4 没有现成工具的来源

agent 用应用自带的读表脚本把 xlsx、csv、pdf 转成文本（留给实现者选库），自己转成分录，写进暂存文件，过一遍 §6.3 的脚本，把汇总（笔数、总额、起止日期、对上和拿不准的）给用户看，用户确认后才写入账本。

### 6.5 每个来源的说明

skill 里每个来源一份说明文件，写：在哪里导出（菜单路径）、导出什么格式（压缩包、密码从哪来）、用 deb 的哪个 provider 或走 §6.4、已知的坑（例如微信一次最多三个月）。第一批来源：支付宝、微信、美团、京东、建设银行、工商银行、上海银行、宁波银行。用户以后用到其他银行，照同样的格式加。

## 7. 投资、借贷、报销

- **投资（基础版）**：用户在聊天里说买卖了什么、多少份、多少钱，agent 按份额和成本记。每个投资品在 `accounts.beancount` 的 commodity 指令里写价格源，定时任务用 `bean-price` 现成的价格源抓价格，追加到 `prices.beancount`；抓不到的只在回复里报告，不影响记账。导入账单时遇到看起来是投资买卖的行（基金申购、证券转账等），不当成消费记，列给用户确认。进阶功能见 §2 非目标。
- **借贷**：借出记到借款人的应收账户，还款冲掉；借入同理记应付。
- **报销**：垫付时支出记到"应收报销"，到账时冲掉。
- 问"谁还欠我钱""哪些报销还没到账"时，agent 查这些账户的余额回答；月度小结里列出来。

## 8. 安装和设置

### 8.1 软件（`app.toml` 的 `requires`）

- beancount、beanquery、beanprice 和 Fava 装进同一个 uv 工具环境，一并暴露 `fava`、`bean-check`、`bean-format`、`bean-query`、`bean-price`：

  ```
  uv tool install fava --with-executables-from beancount,beanquery,beanprice
  ```

  应用自己的脚本（去重对账、读表、画图）不用这个环境，由 `uv run` 按脚本里声明的依赖单独准备，画图库也在那里（Claude 定）。脚本要求 Python ≥ 3.11，和依赖一起写在入口脚本的 PEP 723 头里，由 `uv run` 准备。
- double-entry-generator：下载官方发布的安装包放进 `~/.local/bin`，不需要 root；各平台的安装行留给实现者。
- `uv`：总站本来就靠它装 cc-hub，脚本也用它跑（留给实现者决定脚本怎么取得 beancount 等依赖）。
- 用户的服务器通过代理访问外网（GitHub、价格源）。应用不自己配代理，靠 agent 进程环境里已有的代理变量；cc-connect 以服务运行时，代理变量要和 PATH 一样写进它的 agent 环境配置，README 里提一句。

### 8.2 `SETUP.md` 的步骤

每一步先检查再做，可以重复执行。

1. **个人设置**（`ledger/config.toml` 还没填时）：在聊天里问主币种；从哪天开始记，以及这一天各账户的余额（写成期初余额）；每张卡的银行和尾号；有哪些信用卡；支付宝和微信各用了哪些子账户；用户在聊天里说"微信付的""支付宝付的"时默认记到哪个账户；平时用哪些账单来源；要不要在手机上看 Fava（第 3 步的 Tailscale）。写进 `config.toml`、`accounts.beancount`、期初余额，以及 `importers/` 里各来源的"支付方式对应账户"。
2. **Fava 常驻**：
   - Linux：用户级 systemd 服务，只监听 `127.0.0.1`，端口默认 5000（设置时可改），失败自动重启。要让服务在用户未登录时也运行需要 `loginctl enable-linger`，用户同意就开启；用户不同意或做不到（例如要 sudo）时，把命令告诉用户，说明 Fava 会在用户退出登录时停下、登录后再启动，设置照常往下走，不为它标记 `waiting`。
   - macOS：用户级 launchd。
   - Windows：不常驻，用户要看时 agent 在后台启动。
   - Fava 不设只读，用户可以在网页上改账（Claude 定）；Fava 发现文件在磁盘上被改过会拒绝保存，不会覆盖 agent 的改动；网页上的改动按 §5.3 第 1 条提交。
3. **Tailscale（可选）**：第 1 步里用户说了要在手机上看 Fava 才做：检查 `tailscale` 是否已装好并登录；用 `tailscale serve` 只在 tailnet 内以 HTTPS 提供 Fava；把手机上要打开的地址告诉用户，并说明手机上也要装 Tailscale、登录同一个账号。安装或授权需要 root 的，把步骤给用户，标记 `waiting`。
4. 定时任务的登记和收尾由 `hub-apps` 的通用流程完成。

### 8.3 `REMOVE.md`

停掉并删除 Fava 服务；撤掉 `tailscale serve` 里 Fava 那一项（只撤本应用加的）；告诉用户账本留在 `ledger/`。

## 9. 图表

- 用户在聊天里要图（"把这个月的支出画张图发我"），agent 用应用自带的画图脚本从账本生成 PNG，再用 `cc-connect send --image <路径>` 发到聊天里（cc-connect v1.5.0 已有这个参数）。
- 至少支持：某段时间按类别的支出、按月的收支趋势、净资产变化；其他图 agent 可以按需用同一个脚本的参数组合（留给实现者定参数设计）。
- 图片生成在不进 git 的临时位置，发完即可删。
- 图上的文字可能是中文（类别、商户、标题）。服务器上没有中文字体时会显示成方块，实现者要处理：检测可用字体，必要时提示用户安装或退回英文标签。

## 10. 定时任务

| 任务 | 时间 | 做什么 |
|---|---|---|
| `prices` | 工作日 18:00（服务器本地时间） | 用 bean-price 更新投资价格，校验、提交。没有投资品时什么也不做。回复只用一行。 |
| `monthly` | 每月 1 号 09:00 | 提醒用户导出上个月的账单，按 `config.toml` 里用户用到的来源列清单；列出未收回的借款和未到账的报销。不发小结，因为这时上个月的账单还没导。 |

上个月的收支小结（按类别、和上月比、净资产变化，附一张图）在导入结束时发：agent 导完一批账单后问用户"还有别的账单吗"，用户说导完了，再按 §6.2 第 6 条核对余额，然后发小结。用户之后又补导了，就再发一份更新后的小结。

两个任务都 `default: true`、`session: new_per_run`。cron 任务每次运行的回复都会发到聊天里，`prices` 每个工作日都会发一条，所以提示词要求回复尽量短（Claude 定；实现者确认 cc-connect 有没有办法让任务不发消息，有就在没变化时不发）。

## 13. 开发和测试

- 脚本（去重对账、读表、画图）都要有自动测试，用合成的账单样例覆盖 §6.2 的各种情形。合成样例照 double-entry-generator 仓库自带的各来源示例账单的格式来造，不用用户的真实账单。CI 留给实现者决定。
- 真实账单只在用户第一次真正导入时使用，那一次就是验收：agent 先给汇总、用户确认后才写入。发现格式和设想不同的，修脚本并补一个合成样例。真实账单永远不进 tap 仓库。
- 各家银行的卡是储蓄卡还是信用卡，在设置时问用户（§8.2），开发时不需要预先知道。
- 开发时在 WSL 的总站里用 `cc-hub app install /mnt/c/dev/hub-apps/ledger --link --yes` 装，改了马上生效。WSL 上现有的 `~/.cc-hub` 是 0.3.0 模板、没有完成首次运行，实现者可以另建一个测试用的总站（`CC_HUB_DIR`）。
- WSL 上目前没有原生的 cc-connect，所以聊天里的端到端验证（定时任务、发图、收账单文件）要等 cc-connect 在 WSL 装好；在那之前，直接在总站目录里开 Claude Code 验证 skill 和设置流程。
- 应用写完后，用一份合成的账本和账单完整走一遍：安装 → 设置 → 记账 → 导入（含重复和转账）→ 问账 → 发图 → Fava 访问 → 卸载。
