# plans 应用设计

日期：2026-10-12，2026-10-19 更新
所属 tap：`hub-apps`（公开仓库 `Jenwein/hub-apps`）
目标 cc-hub 版本：0.7.0，带定时任务时间覆盖和汇报机制（见 `Jenwein/cc-hub` 的 `docs/superpowers/specs/2026-10-12-cron-overrides-design.md`、`docs/superpowers/specs/2026-10-16-reports-design.md`，用法见它的 `docs/apps.md` "Reports"）

标注约定：没有标注的内容是用户的决定；标"（Claude 定）"的是 Claude 替用户做的选择，用户可以改；标"（留给实现者）"的由实现者决定。

## 1. 这是什么，为什么做

用户希望任何 agent 连上总站后，都成为像《钢铁侠》里贾维斯那样的助理：了解你，盯着你的事，主动开口，一个入口办所有事。`plans` 补上"盯着你的事"这一块：和用户一起定人生目标和计划，按计划每天提醒、接受打卡、定期回顾。

这个应用公开发布，任何 cc-hub 用户都能装；计划和打卡记录是每个用户的私人数据，只存在他自己的总站里。

应用只提供通用的机制：目标、计划、事项、安排、提醒、打卡、暂停、回顾。具体领域的做法，例如健身练什么、没练的那次怎么补、求职每天刷几道题，不写进应用，而是写进每份计划里，由 agent 和用户一起定。

## 2. 目标、非目标、绝对不能出的错

**目标**

- 两层目标：长期的"大阶段"和短期的"规划"（§4）。
- agent 先出计划方案，用户改到满意、确认后才生效。
- 今天各规划要做的具体内容是总站日报里本应用的一段；晚上只在还有事没打卡时单独问一次（§6）。
- 打卡随意：白天任何时候在聊天里说一句就算，顺口说的数字也记下来；可以休息、暂停。
- 每周回顾、每月回顾分别是周报、月报里本应用的一段；规划到期总结（§7）。
- 同时进行多个规划时，日报里的一段和晚上那一问都把所有规划合在一起。

**非目标**

- 把任何具体领域的规则写进应用（健身、学习、求职等都只是计划的内容）。
- 与飞书日历等外部日历同步（Claude 定：这次不做）。
- 本应用自己登记早上、每周、每月的定时任务：这些内容都走 cc-hub 的汇报（§6、§7）。
- 人生百科（另一个应用）。
- 徽章、积分等游戏化设计（Claude 定）。
- 多人共享的计划。

**绝对不能出的错**

1. 刷屏和反复催：所有规划合起来，本应用自己一天最多发一条消息（晚上那一问），今天的清单只是日报里的一段；晚上那条只在有事没打卡时发，只问一次，不追问，第二天不翻旧账（§6）。
2. 说教或施压的口气。没完成的事只在回顾里就事论事地说。
3. 没经用户同意就改计划。agent 可以建议调整，用户确认后才改。
4. 编造或数错统计数字。今天该做什么、完成率、连续天数、数字趋势都由脚本算（§9）。
5. 在暂停或休息的日子里提醒，或把那天的事列进日报。

## 3. 国际化

给 agent 读的文字（skill、`SETUP.md`、定时任务和汇报段落的正文）用英文写；agent 跟用户说用户的语言；计划内容和打卡记录用用户的语言。脚本段（§6）的框架文字由脚本按 cc-hub 给的 `CC_HUB_LANGUAGE` 写。

## 4. 目标的两层

**大阶段**，例如"未来三年转行做独立开发"：

- 写方向、为什么做、时间范围、几个里程碑（例如"半年内上线第一个作品"）。
- 不需要每天打卡。

**规划**，例如"这三个月学完前端基础""开始健身"：

- 可以挂在某个大阶段下面，也可以独立存在。
- 内容：目标、为什么做、开始和结束日期（可以没有结束日期，即"长期习惯"，例如每天喝水、吃药）、事项和安排、要跟踪的数字、检查点、这份计划自己的规矩（例如没做的那次怎么办）。
- 安排的通用形式（Claude 定）：
  - 每天做；
  - 按星期固定（例如每周一、三、五）；
  - 每周若干次、哪天都行（例如每周跑 3 次）；
  - 按顺序轮换（例如三分化：胸、背、腿依次轮），可以和"按星期固定"组合（例如周一、三、五轮换胸、背、腿）；
  - 每一项可以带具体内容（动作、组数、要读的章节等），提醒时原样列出。
- 轮换怎么往下走，只有两种与领域无关的推进方式，由用户在定计划时选（Claude 定）：
  - **做完才往下**：某次没做，下次仍是这一项；
  - **按日子往下**：不管做没做，每个安排日都轮到下一项。
  计划自己的其他规矩（例如"没练的那次挪到休息日补"）写在计划正文里，由 agent 照着执行：它用脚本的"改期"命令把某一次挪到别的日子，脚本据此算出每天该做什么，agent 自己不推算日期。
- **检查点**（规划）和**里程碑**（大阶段）都是带日期的结构化条目（Claude 定）：一句描述，可选一个数字目标（例如"第 6 周：5 公里跑进 30 分钟""体重 70 公斤"）。检查点到日子时出现在当天日报里本应用的一段和当周回顾里；里程碑由用户确认达成（agent 只能提议标记），过了日期还没达成的在每月回顾里指出。

## 5. 定计划

1. 用户说出想做的事。agent 先问几句关键情况（现在的状况、每周能投入多少时间、限制条件），然后出一份完整方案：事项、安排、每项的具体内容、要跟踪的数字、检查点、没做时的规矩。
2. agent 出方案时可以参考通用的公开知识（例如常见的训练计划结构），但不把用户的个人信息发到外面（Claude 定）。
3. 用户改到满意、明确确认后，计划才生效并存下来；没确认的方案不进日报，也不发提醒。
4. 计划中途调整也一样：agent 提出改法，用户确认后才改；计划文件里记一行"哪天改了什么、为什么"。

## 6. 每天

**日报里的一段**（`reports/daily.md`）：

- 时间就是总站日报的时间：默认每天 08:00，用户用 `cc-hub cron set report-daily "0 7 * * *"` 这样的命令改，改的是整份日报，其他应用的段落一起挪。
- 列出日报发出那天所有进行中的规划要做的事，带上每项的具体内容（例如"今天练背：引体向上 4×8、杠铃划船 4×10……"），以及当天到期的检查点。
- 那天没有任何事要做时这一段为空，日报里就没有它；所有段落和留言都为空时，cc-hub 整份日报都不发。
- 规划到期的第二天，这一段附上到期总结的邀请（§7）。
- 日报没打开时这一段发不出去。设置时 `hub-apps` skill 会问要不要打开本应用供稿的日报、周报、月报；用户不开日报，就没有早上的清单，只有晚上那一问（Claude 定）。
- 用脚本段还是说明段（留给实现者）：脚本段由 cc-hub 直接运行，输出原样进日报，不用 agent 写字，但要用户在这台机器上批准命令；说明段由写日报的 agent 照脚本算出的清单写。两种都只用脚本算出的内容，agent 不自己推算（§2 第 4 条）。

**晚上一条**（定时任务 `evening`，默认 21:00，可改）：

- 只在今天还有事没打卡时发，只问一次，例如"今天的背部训练练了吗？"。
- 没有要问的事时回复 `NO_REPLY`：cc-hub 登记的定时任务都是静默的，这时聊天里什么也不出现。
- 这一问要用户当场回答，所以单独发，不进日报，也不用 `cc-hub report note` 留给报告。
- 用户不回就算了；不追问，第二天不翻旧账，只在回顾里体现。

**打卡**：

- 白天任何时候说"练完了""今天背了 30 个单词""体重 72.5"都算；带数字的记下数字。
- 可以只完成一部分，记为部分完成。
- "今天休息""这周出差，暂停健身"：对应日子不提醒、不列进日报，也不算没完成。暂停可以指定截止日期，到期自动恢复（Claude 定）。
- 打卡后简短回一句确认，不额外说教。

## 7. 回顾

- **每周回顾**是周报里本应用的一段（`reports/weekly.md`，时间是总站周报的时间，默认周日 20:00）：每个规划这周完成了几次、计划是几次、连续天数、没做的原因（用户说过的），以及要跟踪的数字的变化；就事论事；问要不要调整计划。
- **每月回顾**是月报里本应用的一段（`reports/monthly.md`，时间是总站月报的时间，默认每月 1 号 09:00）：每个大阶段的里程碑走到哪了，下面的规划是不是还在朝这个方向走，要不要开下一个规划。
- 两段都是说明段（Claude 定）：要判断"是不是还在朝这个方向走"、要转述用户说过的原因，脚本写不出来；数字全部来自脚本。
- 用户在聊天里回复回顾里的问题（例如"健身那份改成每周 3 次"）时，agent 照 cc-hub 的规则读最近一份对应的报告存档来接上，改计划仍要用户确认（§5）。
- **到期总结**：规划结束后，问用户要不要做一次总结：目标达到没有、哪些做法管用、要不要定下一阶段。邀请放在日报的一段里（§6）。
- cc-hub 的汇报只发文字，回顾里的趋势用文字和数字写（例如"体重 72.5 → 71.8"）；用户想看图时在聊天里说，agent 用脚本画图，用 `cc-connect send --image` 发送（Claude 定）。
- 没有进行中的规划时，所有回顾段都为空，不进报告。
- 回顾不另存：发出的报告由总站存档在 `reports/` 下、随总站提交；写回顾时要的统计都由脚本从打卡记录重算，不读报告存档（Claude 定）。

## 8. 不发消息的做法

- 定时任务：没事就回复 `NO_REPLY`，聊天里什么也不出现。
- 汇报段落：说明段没话说就不存（不调用 `cc-hub report put`），脚本段没话说就什么也不输出；空的段落不进报告。

## 9. 应用的组成

- **app.toml**：应用名 `plans`，数据目录 `plans`，依赖 `uv`，`min_hub = "0.7.0"`（有 `reports/` 目录的应用都要这个版本）。
- **数据目录**（Claude 定，具体格式留给实现者）：
  - 每个大阶段、每个规划各一个 Markdown 文件，开头是结构化的字段（日期、状态、安排、事项、数字定义），正文是目标、为什么、规矩、检查点和修改记录；
  - 打卡记录按月一个文件，每条一行（日期、规划、事项、完成情况、数字、备注）。
- **脚本**：一个用 `uv run` 跑的小脚本，负责：算出某一天每个规划该做什么（考虑安排形式、轮换推进方式、改期、暂停和休息），以及当天到期的检查点；记一条打卡；把某一次改期；算完成率、连续天数、数字趋势；用户要看时画图。日报一段用脚本段的话，也由它输出这一段。agent 不自己推算日期或数数。
- **skill**：一个 `plans` skill，`SKILL.md` 讲总规则（私聊、确认后才改计划、提醒的规矩、写入后提交），细节拆到参考文件：定计划、每天、回顾。
- **定时任务**：只有 `evening`（21:00），`default: true`、`session: new_per_run`，时间能被用户覆盖。
- **汇报段落**：`reports/daily.md`（今天的清单）、`reports/weekly.md`（每周回顾）、`reports/monthly.md`（每月回顾）。
- **SETUP.md**：问用户晚上检查在什么时间，用 `cc-hub cron set plans/evening "30 21 * * *"` 这样的命令写进总站的设置，再按实际生效的时间登记。告诉用户今天的清单、每周回顾、每月回顾跟着总站的日报、周报、月报走，时间是那几份报告的时间。打开这几份报告、批准脚本段的命令，由 `hub-apps` skill 在设置时处理。以后用户在聊天里说"晚上的提醒改成 22 点"，agent 用 `cc-hub cron set plans/evening "0 22 * * *"` 改，并重新登记；说"早上的清单改成 7 点"，agent 先说明这会挪动整份日报，用户同意后用 `cc-hub cron set report-daily "0 7 * * *"` 改，并重新登记。
- **README**：在 tap 的 README 里加一节，说明这个应用做什么、怎么用。

## 10. 开发和测试

- 本应用要的 cc-hub 0.7.0 已在 PyPI 上，安装测试和 CI 用它。

- 脚本有自动测试，用合成的计划和打卡记录，覆盖：各种安排形式下"今天该做什么"、轮换推进、暂停和休息、跨月、完成率和连续天数、数字趋势、长期习惯（没有结束日期）。日报一段用脚本段的话，还覆盖它在没事、中文、英文时的输出。
- skill、定时任务和汇报段落的文字有一致性测试（链接有效、提到的脚本命令存在、frontmatter 合法），沿用 `ledger` 的做法。
- 应用通过 cc-hub 实际安装一遍（沿用 `ledger` 的安装测试）：设置时写入定时任务时间覆盖；`cc-hub report list` 列出日报、周报、月报三段；`cc-hub cron list` 里本应用只有 `plans/evening`。
